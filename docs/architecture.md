# How bowel works

The product logic is in [product-ia.md](product-ia.md); the approved interaction prototype is [prototype/index.html](../prototype/index.html). How to build and run is in the [README](../README.md#develop).

## Design

- **Providers supply nodes.** A subscription URL, pasted node links (`vmess://`, `trojan://`, `hysteria2://`, …) or a YAML file each become a mihomo `type: file` proxy-provider. bowel downloads subscriptions itself, to read their usage and expiry. A hidden per-provider suffix keeps node names unique across providers.
- **Routes come from bowel's template** (`internal/routes`): 默认, AI 服务, 流媒体, 开发 and 直连, and the rules that recognise each. Every node can serve every route. Each proxied route has two groups: a selector, and an automatic url-test group the selector can point at ("自动" = fastest + failover).
- **Your own rules come first** (`internal/routes/user.go`, `ui_rules.go`). A rule sends a domain and its subdomains, one name, a keyword or an IP range to a route; they are kept in settings.json and written before the template's. The quickest way to make one is 让它走… on a connection in 日志, which offers the site (api.openai.com → openai.com) or the one name. 设置 > 规则 adds them by hand, says what a typed rule will do before it is added, moves and removes them, and tests an address. A change closes the open connections it would send elsewhere, so it shows at once.
- **Rule sets** (`internal/ruleset`, `app_rulesets.go`, `ui_rulesets.go`). A list of rules kept by someone else, from a link or a local file (mihomo YAML, or `.list` text), is a service of a route group, so it moves, switches off and goes like any other. bowel fetches and checks it itself: 导入 shows the rule count before anything counts, lines the core can't use are left out and counted, and the core is given a clean `type: file` rule-provider. That also lets 测试一个地址 look inside a set, which the core has no call for. Links update daily; a failed update keeps the last good list and says so on its row. An update replaces the file and asks the core to read it again (`PUT /providers/rules/…`), so it closes nothing. The order of the three is fixed: your rules, then rule sets, then the template's. Among themselves the sets go as 路由组 lists them, by their group and then their place in it, with 其他流量's last; groups and the sets of a group are dragged to reorder them (`Plan.MoveGroup`, `Plan.MoveRuleSet`). Developer networks come before all of them, so a remote list can't take the LAN or the tailnet. With no rule set in use, your rules and the template's stay sorted together by how specific they are. Rule sets are always `no-resolve`, as your own IP rules are, so a set can't add a DNS lookup to every connection. `IP-ASN` rules need the core's ASN database, which it downloads itself on first use. Desktop only for now: the mobile apps don't import sets, and agents can only read them (`list_rules`, `explain`).
- **A provider's own routing** (`internal/core/imported.go`, `app_imported.go`, `ui_imported.go`). A complete Clash config often brings its own `proxy-groups` and `rules`. These stay unused until the user picks 使用它们 on that provider's row, because most subscriptions bring groups and an update must not change anyone's routing by itself. One provider at a time; `settings.ImportedRouting` names it. While it is in use bowel gives the core that config's nodes, groups, rules, sub-rules and the rule and proxy providers they use, unchanged, and nothing else from it: ports, DNS, TUN, listeners, the controller and scripts are bowel's or ignored. The nodes go at the top level under their own names. A group's `proxies:` can't name a proxy-provider's nodes, so the suffixed copies could not be referenced; unchanged names also mean no reference needs rewriting and a `filter` still means what it meant. The provider's `p-<id>` copy stays for the node list, tests and the location probe, and `listedNode` maps one name to the other. `include-all*` is expanded to the source's own members, so a group doesn't take in bowel's providers or the developer networks' outbounds. Remote providers are the core's to download, with the source's `path` removed; a used `type: file` is refused, as a path means nothing on this machine. Groups that rules point at become routes, so 今日, the map, 活动 and the menu bar work unchanged and MATCH's target is the default route; 路由组 lists every group, and only `select` groups can be switched. The user's rules and rule sets pause and come back with bowel's routing; developer networks still come first. 测试一个地址 and MCP's `explain` don't work here, since the core has no call for it and bowel can't evaluate rules it didn't write. An update of the provider in use is checked first, by reference and with `mihomo -t`: if it fails, or no longer has groups, the last good file stays and the error shows. It never falls back to the template. Disabling the provider goes to bowel's routing until it is enabled again; deleting it ends the choice. Desktop only for now.
- **The core runs as a sidecar process** (`internal/core`), controlled over a unix socket. bowel falls back to TCP with a secret when the socket path is too long. Config changes reload the core without restarting it.
- **The interface is native.** The window and the menu bar panel are MyGo `ui` views over two values: a `Snapshot`, rebuilt whenever anything changes, and a `Tick`, every second. The 今日 board animates its cells' boxes: the expanded cell grows in place and the others are squeezed into summaries chosen to fit. Every view is laid out at its cell's final size, so nothing reflows on the way. Views open and fold like drawers, and shared pieces fly between views (`Match`, with text morphing).
- **Status is measured, not assumed** (§2 of the IA). bowel checks every 2 s that the system proxy still points at it (`scutil --proxy` on macOS, WinINet's settings on Windows, GNOME's or KDE's on Linux). The core's state, failing nodes and automatic switches feed the one light: 正常 / 降级 / 异常 / 未接管.
- **Exit locations** (`internal/locate`, `internal/geo`). A node's place is guessed from its name. When it matters (the node a route uses, or one you pick), bowel measures it instead: it requests Cloudflare's `/cdn-cgi/trace` through the node, via a mihomo listener bound to a probe group. The UI labels each place 实测 / 按名称 / 未知.
- **Monitoring** (`internal/monitor`). bowel polls connections every second while the window or the menu bar panel is open (every 5 s otherwise) to get rates per route and per app, new connections, and closed ones. It parses failed dials from the core's log, and keeps today's and this month's totals. On macOS 27 the kernel hides its socket list from a process whose parent is an ad-hoc signed app, so the core, bowel's child, cannot tell which app opened a connection. bowel reads the list itself (`internal/procinfo`) and names those connections. Under `mygo dev` bowel is itself such a child, so the names show as 未知 in development; an app opened from Finder has them.
- **TUN.** The first time you turn it on, the system asks for an administrator's authorisation, and what that buys is each system's own (`internal/tun`). On macOS bowel copies the core to `~/Library/Application Support/bowel/bin/` and makes it setuid root, the approach early Clash Verge used; a launchd helper would be the cleaner long-term design. On Linux the copy (in bowel's data directory) is given to root and the file capabilities TUN needs (`cap_net_admin`, `cap_net_bind_service`, `cap_net_raw`) under one `pkexec`, so the core still runs as the user; without `setcap` it is setuid root, and a data directory mounted `nosuid` is refused. Where systemd-resolved is in use the same `pkexec` leaves a polkit rule for the user (`/etc/polkit-1/rules.d/49-bowel-tun-<uid>.rules`), since the core calls `resolvectl` for the TUN device at every start and polkit would ask each time; `docs/platform-parity.md` says what it allows. On Windows nothing lets a program be elevated without asking, so the one UAC prompt copies the core to `%ProgramData%\bowel\tun\<SID>\`, which only administrators can write, and registers a scheduled task of the user's that runs it at the highest run level (and a second one for accounts the first cannot start for, which runs it through a copy of bowel's own program kept in the same directory, so that ending the task ends the core). The user may start and end their own task unasked, so the core manager does that in place of starting a child (`Manager.Spawn`), waits on the process, and reads its log from the controller, since such a core prints to no one. The copy does not follow an update of the app: when its version differs from the bundled core's, bowel runs the bundled core if TUN is off, and otherwise keeps the old copy and offers to replace it, which takes one authorization. The new copy replaces the old one only after that authorization.
- **Gateway mode** (`internal/gateway`, `app_gateway.go`, `ui_gateway.go`). One switch lets other devices on the LAN set their gateway and DNS to this computer and follow bowel's rules. On macOS and Linux bowel turns IPv4 forwarding on through a sudoers rule that allows exactly the two `sysctl` commands (checked with `visudo`, installed in the same prompt as TUN), keeps the computer awake (`caffeinate`; a `systemd-inhibit` lock that ends with bowel's process), and puts DNS on `0.0.0.0:53` with fake-ip. The original forwarding value is kept in `gateway-before.json`, so a crash is undone on the next start. Forwarding, port 53 and TUN are measured; a gateway that is wanted but doesn't work makes the state 降级. Windows has no gateway yet, and the interface doesn't offer one there: forwarding is per adapter and needs elevation each time, and the firewall needs rules of its own (`docs/platform-parity.md`).
- **Skins** (`skins.go`). Thirteen looks for the whole interface: 纸墨 Paper (the default), 报刊 Broadsheet, 荧光屏 Phosphor, 霓虹 Neon, 蓝图 Blueprint, 樱 Sakura, 山水 Shanshui, 青瓷 Celadon, 敦煌 Dunhuang, 暮色 Dusk, 极光 Aurora, 黑曜 Obsidian and 孔版 Riso. A skin is a palette, the faces of text and big type, corner roundness, a glow and a texture; what the interface does is the same in every skin.
- **Developer networks** (`internal/devnet`, `app_devnet.go`, `ui_devnet.go`; cases and reasons in `docs/dev-network.md`). A catalog of what is local everywhere, plus what bowel reads of this machine every 20 seconds (Tailscale, VPN routes, split DNS: `netstat` and `scutil` on macOS, iproute2 and systemd-resolved on Linux, the IP helper API and the name resolution policy table on Windows), compile into an overlay on the core's config and the system proxy's bypass list. It is never saved, so no migration and nothing left behind. Tailscale and VPNs get a direct outbound bound to their interface, because under TUN the core's DIRECT uses the default interface. In global and direct mode the core runs in rule mode with the overlay and a single `MATCH`, so the LAN and the tailnet are not sent to a node.
- **IPv6 modes** (`core.IPv6Mode`, `internal/devnet/ipv6.go`, `app_devnet.go`). The setting is Off, Auto or On, Auto by default. Auto keeps IPv6 only while the interface traffic leaves by has a public (`2000::/3`) address and a TCP connection bound to that interface reaches a public resolver. Being bound keeps bowel's own TUN from answering, and it also proves there is a route, so routes aren't read for it. The check runs with the developer-network poll, tries the network again each minute, and needs two readings in a row to change anything, except losing the address, which counts at once. The result is never saved: like the overlay it only goes into the runtime config, as `ipv6` and `dns.ipv6`. `ipv6: false` is enough for the TUN too: mihomo then gives it no IPv6 address, and sing-tun routes no IPv6 without one. A change reopens the TUN, because its address is part of what the core compares; without TUN the reload interrupts nothing. In `settings.json` Off stays `false`, which older versions read, and Auto and On are strings; a bare `true` is from before the modes and migrates to Auto once. The mobile bridge doesn't read the network, so Auto is On there.
- **Updating itself** (`app_update.go`, `ui_update.go`). A native binary cannot swap its code while it runs, so an update is `mygo.Updater` (signed archive or delta) followed by a restart. bowel checks the latest release 20 s after launch and every 6 hours and shows the new version in the title bar. One click downloads with progress and restarts through the ordinary quit: the system proxy and gateway go back and the core ends, so if the new version fails to come up the Mac keeps its own network. The network drops for a few seconds. Installs the app cannot write to, such as a .deb in /opt, are left to their package manager.
- **Download sources** (`internal/devtools/sources.go`, `ui_sources.go`). npm, PyPI, Go and Rust are already built-in services of 开发, so the route a download takes is the group its service is in. The one thing a rule cannot say is "use a mirror instead", which is the tool's own setting: one line of `~/.npmrc`, `pip.conf`, Go's `env` or `~/.cargo/config.toml`. bowel reads it, and on 用这个 changes that one line where it is, leaving the rest of the file; going back to the official source deletes it. Only the mirrors bowel lists can be written. Every few minutes, and while the section is shown, each way is measured: the mirrors directly, the official address through bowel's own port so that it takes the route its service has (not measured while the core is down). A source whose setting does not answer makes a line on the 模式 cell and offers 修复: the fastest mirror that answers, else the official source, or, when the official address is down because its service was sent to 直连, putting that service back in its default group. This lives in the expanded 模式 cell under 开发工具, not in 路由组, and what belongs to a row there is set in under it with a rule down its left side.
- **Agents (MCP)** (`internal/mcp`, `app_mcp.go`, `ui_mcp.go`). bowel serves an MCP server on a unix socket in its data folder (`mcp.sock`, this user only). `bowel mcp` bridges an agent's stdio to it and opens the app when it isn't running, so an agent registers it as an ordinary stdio server: `claude mcp add --scope user bowel -- /Applications/bowel.app/Contents/MacOS/bowel mcp` (设置 > MCP has the command and a JSON snippet to copy). Agents can always read: status, settings (secrets hidden), routes and nodes, rules, where a host would go, connections, logs, and the three whitelists (direct sites, the system proxy's bypass list, LAN addresses). Changes (mode, takeover, a route's node, rules, whitelists, settings by key, providers, DNS) follow `mcpPolicy`: `ask` (the default: a dialog shows what would change, and can let the rest of that connection through), `allow` or `deny`. Only the user can change the policy. 设置 > MCP lists the changes agents asked for.
- **Command line and daemon** (`internal/cli`, `cli.go`, `app_cli.go`, `app_daemon.go`). bowel runs in two shapes that serve the same thing. The app is one; `bowel daemon` is the other: `newApp` and the same loops, but MyGo's `Run` is never called, so there is no window, tray, Dock icon or self-update, and it ends on SIGINT, SIGTERM or `bowel stop` through the ordinary `shutdown`. Either shape serves a second unix socket beside `mcp.sock`, `cli.sock`, in the same protocol (`internal/mcp`) with the same tool handlers (`mcpServer`) plus a few the command line alone has (`cliTools`: providers add/remove/enable, nodes on a route, gateway, log tail, stop). The commands (`bowel status`, `bowel mode global`, …) are a thin client of it: `internal/cli` parses, calls a tool and prints, as a table for people or as the tool's JSON with `--json`; it holds no product logic. `bowel tui` (`tui.go`, `tui_view.go`, `term_*.go`) is the same client on a whole terminal: one goroutine owns the model and the connection and waits on keys, a one-second clock and the terminal's size; each page is a tool's answer and each key a tool's call, a change asking y/n first. The terminal is driven directly (raw mode through `golang.org/x/sys`, escape sequences for the rest), with no terminal library. `main.go` only decides between the app (no arguments, or what a launcher passes) and `runCLI`. What tells the user from an agent is the socket and what the session says of itself. A session on `cli.sock` is the user's (`isLocal`), so `approve` lets its changes through without asking and they are not listed among the agents'; it may also set `mcpPolicy`. A command that finds an agent's environment (`cli.Agent`: `CLAUDECODE`, `CODEX_SANDBOX`, `CURSOR_AGENT`, `AI_AGENT`, …) says so in `initialize`, and that session is treated exactly as one on `mcp.sock`; so is a session that never initializes. The daemon cannot show the dialog, so under `ask` it refuses. This is a guard rail and not a boundary: a program of the same user that sets out to get round it can clear its environment, or write `settings.json`. A data folder named by `BOWEL_DATA_DIR` or `--data-dir` is told apart by its own sockets; the default one also takes MyGo's single-instance lock, so the app and the daemon never run two cores on one folder.
